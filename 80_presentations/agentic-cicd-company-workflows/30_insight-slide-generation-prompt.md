# Agentic CI/CD 洞察页生成方法与提示词

> [!abstract] 用途
> 本文档是后续公司页与大能力页的统一内容生成输入。它定义页面应完成的沟通任务、论证方法、输出结构和证据边界；具体页面字段继续参考 [[80_presentations/agentic-cicd-company-workflows/20_slide-template|作业流单页模板]]。

## 一、默认沟通任务

默认受众为 CTO、研发效能负责人和平台工程负责人。页面要帮助他们理解：一个公司或能力块如何把 Agent 接入真实 CI/CD 作业，动态推理、工具执行、确定性验证与治理边界如何组合，以及企业可以借鉴什么。

用一句话表达页面任务：

> 读完这一页，受众应理解 **{{分析对象}} 的关键机制与行动边界**，因为 **{{页面唯一主张}}**。

如已提供更具体的受众、使用场合或决策目标，以新输入覆盖默认值。

## 二、页面选题规则

- 全生命周期平台或控制面较完整的厂商，以“公司/生态”为横向维度。
- 专业能力证据集中但单一厂商覆盖有限时，以“大能力块”为横向维度，选择少量代表厂商作为机制证据。
- 每页只承担一个叙事任务和一个主张，不做公司产品全景或功能目录。
- 页面主张必须能够由正文直接证明；标题中的每个核心名词和动作都要在机制或作业流中有对应关系。
- 公司页优先解释其差异化装配方式、数据面或控制面；能力页优先解释共同作业流与成熟边界。

## 三、论证顺序

按以下顺序组织，不从产品列表开始：

1. **主张：** 先写受众应该记住的判断。
2. **机制证据：** 说明哪些真实产品对象、配置、运行阶段或控制结构支撑该判断。
3. **作业流或能力关系：** 展示触发、上下文、Agent、工具、确定性系统、验证与输出如何连接。
4. **控制边界：** 明确身份、权限、沙箱、Policy、Oracle、Approval、预算和回退在哪里生效。
5. **企业启示：** 解释这一机制为什么值得借鉴，以及当前不能外推到什么程度。

如果分析对象本身是编译器、协议、控制面或运行框架，可以使用“定义/装配 → 编译/配置 → 运行 → 外化结果”的机制链代替业务场景作业流。

## 四、页面必须回答的六个问题

1. 什么事件或人类意图触发作业？
2. Agent 获得哪些结构化或非结构化上下文？
3. Agent 负责判断、规划、生成或选择什么？
4. 哪些 Tool、CLI/API、MCP、Pipeline、Runner 或 Runbook 真正执行？
5. 哪个外部 Oracle、Gate 或人类角色证明结果并决定是否继续？
6. 自治停在哪里，能力当前处于 GA、Preview、Beta、EA、Research 还是路线图？

## 五、组件必须映射到具体阶段

不要在页面旁边孤立罗列 Skill、Agent、MCP、Pipeline 或 Oracle。必须说明它们在作业流中的出现阶段和实际职责：

| 组件 | 必须说明的问题 |
|---|---|
| Skill / Rules / Instructions | 在设计时还是运行时加载？它定义的是工作方法、组织知识还是行为限制？ |
| Agent / Engine / Harness | 在哪个运行环境中理解任务和循环调用工具？能否写外部状态？ |
| MCP / CLI / API / Tool | 提供查询还是行动能力？Tool 可调用是否等同获得授权？ |
| Pipeline / Actions / Runner | 负责触发、编排、隔离、确定性执行还是证据留存？ |
| Oracle / Gate | 哪个 Test、Scan、Policy、Signature、SLO 或审批判断成功？ |
| Safe Output / Approval / Runbook | 哪些候选动作可以外化，谁持有最终写权限？ |

如同一组件在设计时和运行时承担不同角色，必须分开标注，不能用一个连续图标暗示其全程运行。

## 六、标准输出结构

每次生成一页内容分析时，按以下九部分输出：

1. **结论型标题：** 一句话表达页面主张，不使用纯公司名或产品名。
2. **页面论证链：** 用一行箭头说明正文如何证明标题。
3. **主作业流或装配机制：** 4—6 个主要步骤；必要时区分设计时与运行时。
4. **组件阶段映射：** Skill、Agent、MCP、Pipeline、Oracle 等分别在哪个阶段生效。
5. **关键功能点：** 只保留支撑主张的功能，每项要回到作业流。
6. **治理与权限边界：** 说明读取、推理、执行、验证和写入权限如何分离。
7. **页底洞察：** 核心差异化、企业启示、当前边界各一句。
8. **状态与证据：** 产品状态、场景自治等级、证据类型、时间点和上游来源。
9. **明确排除：** 写出本页不展开的相邻产品、场景、指标或技术细节。

## 七、证据与成熟度规则

- 研究事实只引用当前工作区中的公司总结、阶段总结、专题深研、Source Brief 和已登记一手资料；PPT 不建立第二套事实源。
- 产品状态与任务自治等级分开：GA 不等于任务成熟，L3 不等于有正向业务价值。
- 自治等级按具体场景、输出、环境和批准方式判断，不给整家公司贴统一等级。
- Preview、Beta、EA、Experimental、Research 和 Roadmap 不写成当前生产标准能力。
- 厂商案例、客户引语和量化数据标明为厂商自述或第一方研究，不外推为行业平均值。
- MCP、CLI 或 API 可调用只代表能力入口；真实授权仍由身份、Token、Policy、环境和审批决定。
- Agent 的自我报告不能充当独立 Oracle；成功需要由外部 Test、Scan、Policy、Signature、SLO 或人类判断证明。

## 八、常见反模式

- **产品功能清单：** 罗列所有 Agent、模块和产品，却没有唯一主张和因果关系。
- **标题与正文脱节：** 标题声称“装配”“闭环”或“控制面”，正文只介绍生命周期或功能名称。
- **把 MCP 等同授权：** 把 Tool Discovery、连接协议和实际写权限混为一谈。
- **把 GA 等同成熟：** 用产品可用状态代替任务可靠性、风险和生产证据。
- **混淆设计时与运行时：** 把 Authoring Skill/MCP 与运行中加载的 Skill/MCP 画成同一组件。
- **单一案例外推：** 用一个修复 PR、客户案例或 Demo 推导端到端 CI/CD 自治。
- **阶段堆砌：** 为了覆盖八阶段而牺牲页面主张和信息层次。
- **权限隐身：** 只画 Agent 和 Tool，不说明哪个系统真正持有写 Token、批准权与成功标准。

## 九、可直接复制的参数化提示词

~~~text
你正在为 Agentic CI/CD 洞察演示编写一页内容分析。

【输入】
- 分析对象：{{公司 / 生态 / 大能力块}}
- 横向维度：{{公司 / 生态 / 大能力块}}
- 目标受众：{{默认：CTO、研发效能负责人、平台工程负责人}}
- 使用场合：{{研究分享 / 决策汇报 / 方案讨论}}
- 上游材料：{{工作区内公司总结、阶段总结、专题深研、Source Brief 路径}}
- 候选主张：{{如有；允许基于证据重写}}
- 产品与能力状态：{{GA / Preview / Beta / EA / Research；包含时间点}}
- 页面限制：{{单页、期望密度、必须包含和明确排除的内容}}

【任务】
围绕一个唯一主张，分析该对象如何把 Agent 接入真实 CI/CD 作业。不要做产品功能清单。标题中的每个核心名词和动作都必须在正文中由真实机制、产品对象或运行阶段直接证明。

按“主张 → 机制证据 → 作业流或装配关系 → 控制边界 → 企业启示”组织内容。若对象是编译器、协议、运行框架或控制面，可使用“定义/装配 → 编译/配置 → 运行 → 外化结果”的机制链，而不是虚构业务场景。

必须回答：
1. 什么触发任务；
2. Agent 获得什么上下文；
3. Agent 负责什么动态判断；
4. Tool、MCP、CLI/API、Pipeline 或 Runner 在哪里执行；
5. 哪个外部 Oracle、Gate 或人类角色判断成功；
6. 自治停在哪里，产品状态和证据成熟到什么程度。

Skill、Agent、MCP、Pipeline、Oracle、Safe Output 等组件不能作为孤立功能罗列。请标明它们在哪个阶段出现、承担什么职责；如存在设计时和运行时两种角色，必须分开说明。

【输出】
1. 结论型标题；
2. 一行页面论证链；
3. 4—6 步主作业流或装配机制；
4. 组件—阶段—职责映射；
5. 支撑主张的关键功能点；
6. 身份、权限、沙箱、Policy、Oracle、Approval 与写入边界；
7. 页底三句话：核心差异化、企业启示、当前边界；
8. 产品状态、任务自治等级、证据类型、时间点和来源；
9. 本页明确不展开的内容。

【硬约束】
- 不发明事实、指标、客户结果或产品状态；
- GA 不等于任务成熟，MCP 可调用不等于获得授权；
- Preview、Beta、EA、Experimental、Research 和 Roadmap 不写成生产基线；
- Agent 的自我判断不能替代外部 Oracle；
- 优先删减低价值细节，不以缩小字号解决信息过载；
- 输出的是页面内容分析，不生成 PPTX、HTML 或视觉成品。
~~~

## 十、归档与使用

1. 先用本提示生成页面内容分析。
2. 将结果归档到对应的 `slides/<编号>-<对象>.md`，该文件作为页面唯一内容源。
3. 在 [[80_presentations/agentic-cicd-company-workflows/source-map|Source Map]] 中核对事实来源与状态。
4. 内容评审通过后，再进入视觉设计和成品生成。

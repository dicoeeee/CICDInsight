## 第 1 页｜智能化 CI 的变化趋势

大家好，今天分享的主题是：智能化 CI 的变化趋势。

这不是一次 AI 编程产品盘点，也不是一场技术方案评审。我更想和大家讨论的是：当 Agent 开始持续搜索代码、修改代码、运行检查、分析失败并再次修复以后，CI 在行业中发生了什么变化？

过去我们习惯把 CI 理解成提交代码之后的最后一道门。最近一个月，从 Asana、GitLab、Harness、AWS、GitHub 以及一项仓库级迁移研究中，我看到 CI 正在逐渐变成 Agent 可以高频消费的工程反馈系统。它不仅要执行检查，还要提供快速反馈、结构化证据、目标验证以及清晰的执行边界。

今天前半部分先讲六条行业变化；后半部分只选择两个近期实践，分别讲 GitLab 和 AWS 自己公开的实现。两个实践不会被拼成一套统一架构，也不要求它们解决前面提出的某个问题。

（翻页）

**来源与边界（不口播）**

- 来源范围：最近一个月 Daily AI Brief 中的 5 家公司实践与 1 项研究。
- 具体一手来源在后续页面逐项标注。

### 讲者理解补充（不口播）

**这页真正想表达什么：** 主题不是“有哪些 AI 功能”，而是 Agent 的工作方式正在反过来改变 CI。传统开发者通常完成一轮修改后才等待 CI；Agent 会连续修改和验证，因此更依赖快速、稳定、结构化的反馈。

**CI 和 CD 的区别：** CI 是持续集成，重点是代码合入前后的构建、测试和质量验证；CD 可以指持续交付或持续部署，重点是把已经验证的变更推进到环境或生产。本次虽然观察整个 CI/CD 行业，但主线优先放在 CI。

**“Agent 高频消费反馈”是什么意思：** 可以把 Agent 想成一个不断进行“修改—检查—再修改”的自动开发者。CI 每返回一次结果，Agent 就可能根据结果开始下一轮工作，所以反馈不是给人看的终点报告，而是 Agent 下一步行动的输入。

**现场被问“什么叫智能化 CI”时：** 可以回答：“不是在流水线里增加聊天功能，而是让系统能为 Agent 提供更快的检查、更明确的失败上下文、更可靠的验证和更严格的执行边界。”

## 第 2 页｜三组数据，一个矛盾

先看三组数据。前两组代表速度，第三组代表可信度。

第一组来自 Asana。他们原本判断，如果继续按传统方式迁移 Enzyme，工作可能还会持续很多年。但在一个目标清晰、可以按目录切分的任务中，他们让多个 Coding Agent 并行工作，最终在大约两个日历周内完成迁移。

第二组来自 GitLab。页面中间的“最高 50 倍”，并不是说所有 GitLab CI 都会快 50 倍。它指 GitLab 在 Next-generation SCM 的早期内部测试中，使用服务器侧 Batch Read、Diff-stat 等接口，替代 Agent 完整 Clone 仓库后再搜索，得到的任务总耗时最高改善上限。它是测试最高值，不是平均结果，也不是生产 SLA。

第三组来自 SWE Refactor Bench。研究覆盖 20 个仓库级迁移任务、520 次运行。最终同时通过迁移目标审计、固定行为测试和独立验证的，只有 28 次，也就是 5.4%。

三组数据放在一起，出现了一个很清楚的矛盾：输出速度和取证速度正在跃升，但完整验证通过的可信结果没有同步增长。

三组证据的身份也不同。Asana 是单一企业案例；GitLab 是厂商内部早期测试；SWE Refactor 是预印本。今天引用这些数字，是为了说明变化方向，不是把个案外推为行业平均值。

（停顿）所以真正需要讨论的，不只是 Agent 能生成多少代码，而是系统能交付多少个经过验证的工程结果。

**来源与边界（不口播）**

- [Asana｜We migrated off Enzyme in 2 weeks](https://asana.com/inside-asana/migrating-off-enzyme-2-weeks)
- [GitLab｜Git was built for humans — agents need an upgrade](https://about.gitlab.com/blog/gitlab-next-gen-scm/)
- [SWE Refactor Bench｜arXiv:2608.23564](https://arxiv.org/abs/2608.23564)
- 边界：单一企业案例 / 厂商内部测试上限 / 预印本。

### 讲者理解补充（不口播）

**为什么把三组数据放在一起：** Asana 和 GitLab 都在说明“速度可能显著提升”，但 SWE Refactor 在提醒“速度提升不等于正确完成”。这一页的重点不是比较三个数字，而是制造速度与可信度之间的张力。

**“最高 50 倍”具体是什么：** 它比较的是 GitLab 内部测试中，Agent 使用服务器侧接口取证，与传统“完整 Clone 仓库后再搜索”之间的任务总耗时。它不是模型快了 50 倍，也不是整个 CI 流水线快了 50 倍。因为是最高值，所以不能理解为平均收益。

**5.4% 怎么算：** 520 次运行中只有 28 次同时通过三层验证，`28 ÷ 520 ≈ 5.4%`。这里的“三层”是迁移目标审计、固定行为测试和独立验证，并不是普通单元测试通过率。

**三种证据强度怎么区分：** 企业案例说明“这件事至少在一个真实环境发生过”；厂商内部测试说明“产品在特定条件下可能达到这个方向”；预印本说明“有一套公开研究方法和数据，但还没有完成同行评审”。演讲时不要把三者说成同等强度。

**如果有人追问能否复制这些数字：** 回答“不能直接复制数字，可以研究它们背后的机制和适用条件”。

## 第 3 页｜生成变快，证明必须更强

由此，我把这次分享的核心判断压缩成一句话：生成正在变快，证明必须更强。

Agent 是概率性的执行者。它可以提出一个修改，也可以解释为什么它认为修改正确，但解释本身不能成为工程事实。工程事实仍然要由真实的类型检查、编译、测试、安全扫描、制品验证和目标审计产生。

所以智能化 CI 不是给流水线增加一个聊天入口，而是把 CI 变成 Agent 可以高频消费的可信反馈系统。Agent 可以探索，可以提出假设，也可以失败；CI 负责产生可以重复执行、可以复查、也可以否定 Agent 判断的证据。

接下来的六条变化，大体可以归到反馈、取证、验证、授权和执行边界几个方向。

**综合来源（不口播）**

- [Asana](https://asana.com/inside-asana/migrating-off-enzyme-2-weeks)
- [GitLab](https://about.gitlab.com/blog/gitlab-next-gen-scm/)
- [SWE Refactor](https://arxiv.org/abs/2608.23564)
- 本页是对开场三项证据的洞察归纳，不是任何一家公司的产品表述。

### 讲者理解补充（不口播）

**为什么 Agent 的解释不能算证明：** Agent 生成的代码和解释都来自概率模型。它可能非常有说服力，但仍可能遗漏文件、误读日志或为了通过检查而采用错误方式。让 Agent 自己说“已经修好”，相当于让被考核者自己给自己打分。

**什么才是工程证据：** 类型检查器真的运行并返回成功；测试在指定环境中通过；扫描器确认告警关闭；制品哈希与被测试对象一致；目标审计确认旧依赖确实被移除。这些结果能够被其他人或机器重复执行。

**“可被否定”为什么重要：** 好的验证不仅能证明一个判断成立，也能明确告诉我们它不成立。例如 Agent 判断“失败由缓存导致”，清理缓存后仍然失败，这个实验就否定了当前判断，应该换一个方向，而不是继续美化解释。

**可以用一句比喻理解：** Agent 像提出答案的学生，CI 像真正运行实验的实验室。学生的推导有价值，但最终结果要由实验确认。

## 第 5 页｜CI 性能正在变成 Agent 产能

先看 Asana 揭示的变化。

传统人工循环是低频的。开发者完成一轮工作以后触发流水线，CI 主要承担合并前准入。即使检查需要十分钟，成本主要表现为人的等待。

Agent 循环不一样。Agent 会连续执行搜索、修改、类型检查、测试、读取失败和再次修复。同样一次十分钟检查，在一个任务中可能被重复很多次。延迟不再只是等待时间，而是被循环次数放大的模型、Runner 和人工介入成本。

Flaky Check 的影响也会放大。人看到偶发失败，可能先判断是否需要重跑；Agent 却可能把噪音当成真实缺陷，修改本来正确的代码。本地与 CI 环境不一致，也会让 Agent 在两套不同事实之间来回修复。

Asana 的文章中，主要人工摩擦并不是 Agent 不会写迁移代码，而是偶尔超过十分钟的 Lint、Flaky Tooling，以及本地和 CI 不一致。

因此在 Agent 场景中，CI 的速度、稳定性和环境一致性开始直接影响单位时间内能够完成多少个“已验证任务”。CI 性能正在变成 Agent 产能。

**来源与归纳边界（不口播）**

- [Asana Engineering｜2026-08-07](https://asana.com/inside-asana/migrating-off-enzyme-2-weeks)
- “CI 性能成为 Agent 产能”是基于 Asana 所述慢 Lint、Flaky Tooling 和环境差异形成的洞察归纳。

### 讲者理解补充（不口播）

**为什么说 CI 性能等于 Agent 产能：** 可以用一个简化关系理解：`任务等待成本 ≈ 循环次数 × 每轮反馈时间`。人类可能一天提交几次，而 Agent 在一个任务中可能进行很多轮验证，所以同样的几分钟延迟会被重复放大。

**Lint 是什么：** Lint 是静态代码规范和潜在错误检查，例如未使用变量、格式问题或不安全写法。它通常比完整测试便宜，但如果配置很慢，仍会成为高频 Agent 循环的瓶颈。

**Flaky Check 是什么：** 同一份代码、相同条件下，有时通过、有时失败的检查。它会制造错误信号。人可以凭经验识别偶发失败，Agent 则可能把它当成代码问题并进行不必要修改。

**本地与 CI 不一致是什么意思：** 例如本地是 macOS，CI 是 Linux；本地依赖已经缓存，CI 从干净环境安装；或者两边使用不同 Node.js 版本。Agent 在本地修好的代码可能在 CI 再次失败，从而重复循环。

**这一页不要误讲成：** “为了 Agent 应该删除慢检查。”真正的方向是分层运行检查、治理不稳定性、改善缓存，并让本地与 CI 尽可能一致。

## 第 6 页｜仓库从“下载代码”变成“查询证据”

第二个变化发生在 Agent 获取仓库上下文的方式上。

今天很多 Agent 仍然沿用面向人的 Git 操作：先完整 Clone 工作树，再运行 grep、diff、blame 等通用命令。每启动一个新 Agent、一个隔离副本或者一次重试，都可能重复下载和解析相同数据。

但 Agent 真正需要的通常不是整个仓库，而是一个小而明确的证据集合：几个文件的当前内容、两次提交的 Diff-stat、某条路径的最后一次变更，或者某个文件的历史。

GitLab 的 Next-generation SCM 把这些操作变成服务器侧接口，例如 Batch Read、Diff-stat 和 Last Commit for Path。仓库不再只提供下载，而是直接回答 Agent 的工程取证问题。

这条趋势的重点不是某个倍率，而是上下文取证正在从模型的搜索技巧下沉到 SCM 基础设施。与此同时，GitLab 的产品仍然处于私有测试阶段，因此这里看到的是架构方向，不是成熟生产能力的承诺。

**来源与状态（不口播）**

- [GitLab｜Git was built for humans — agents need an upgrade｜2026-08-26](https://about.gitlab.com/blog/gitlab-next-gen-scm/)
- 状态：Next-generation SCM 处于私有测试阶段。

### 讲者理解补充（不口播）

**几个 Git 操作分别是什么：** Clone 是把仓库内容复制到本地；grep 是搜索文本；diff 是比较两个版本的变化；blame 用来查看每一行最后由哪次提交修改。传统方式通常要先有本地仓库，才能执行后面这些操作。

**为什么 Agent 不一定需要完整仓库：** 如果任务只是读取三个文件、查看某个路径最近一次变化，下载几 GB 的完整历史明显浪费。服务器侧接口允许 Agent 直接问一个更精确的问题，只取回相关结果。

**“最小证据”是什么意思：** 只让 Agent 看见完成任务必须的文件和历史，而不是默认暴露整个仓库。这样既能减少数据传输，也更容易控制权限和记录访问行为。

**“归因”是什么意思：** 系统可以记录哪个 Agent、哪个工作流、使用什么身份执行了哪次读取或写入。以后出现错误时，可以追查具体动作来源。

**为什么这和 CI 有关系：** CI 诊断经常需要关联失败日志、相关文件、最近提交和依赖变化。如果这些信息能够被结构化查询，Agent 就不必每次从完整仓库和海量日志中重新拼接上下文。

## 第 7 页｜流水线全绿只说明当前检查没有失败

第三个变化，是 CI 开始重新理解什么叫“完成”。

流水线全绿真正说明的只是：当前检查没有发现失败。它并不能自动证明迁移目标、移除目标或者权限收敛目标已经发生。

SWE Refactor Bench 把验证拆成三层。第一层是 Migration Audit，检查迁移动作是否真的完成，例如旧依赖和旧 API 是否已经移除。第二层是固定 Behavioral Tests，验证已知行为。第三层是独立 Agentic Verification，让另外六个 Coding Agent 生成额外测试，主动寻找固定测试没有覆盖的隐藏差异。

研究覆盖 20 个仓库级迁移任务和 520 次运行，其中 340 次通过 Migration Audit，说明迁移动作确实发生；但最终同时通过三层验证的只有 28 次，也就是 5.4%。

它说明只看 Patch 很像对不对不够，只看测试绿不绿也不够。对于迁移、移除和规则收敛这类任务，CI 还需要独立验证“目标真的发生了吗”。

当然，这是一项预印本，而且任务集只有 20 个，不能代表所有 Coding Agent 工作。我们引用的是它揭示的验证缺口，而不是把 5.4% 当成行业成功率。

**来源与边界（不口播）**

- [SWE Refactor Bench｜2026-08-24](https://arxiv.org/abs/2608.23564)
- 边界：预印本；20 个大型迁移任务。

### 讲者理解补充（不口播）

**“流水线全绿”到底证明了什么：** 只证明当前配置的检查都通过了。如果检查本身没有覆盖任务目标，绿色也可能是错误成功。

**一个具体例子：** 任务要求“彻底移除旧测试框架”。Agent 可能保留旧框架，再增加一层兼容代码，让原有测试继续通过。行为没有回归，但迁移目标并未完成，所以需要独立检查旧依赖和旧 API 是否真的消失。

**三层验证的区别：** 迁移目标审计回答“要求的变化发生了吗”；固定行为测试回答“已知功能还正常吗”；独立 Agent 验证尝试回答“固定测试没有想到的地方是否出现差异”。三层检查的是不同问题，不能互相替代。

**为什么独立 Agent 验证仍不等于绝对正确：** 新生成的测试本身也可能遗漏问题或判断错误。它只是在固定测试之外增加另一种搜索隐藏缺陷的方法，不是数学意义上的完整证明。

**现场被问 5.4% 是否说明 Agent 没用时：** 可以回答：“不能这样推断。研究针对的是少量、长周期、整仓迁移任务，说明这类任务的完整验证很难，而不是所有 Agent 任务成功率都只有 5.4%。”

## 第 8 页｜验证开始从语言判断进入真实实验

第四个变化来自 Harness。

RT Agents 被动读取 Harness CD 流水线、Kubernetes 清单和历史执行数据，先预测可能存在的韧性风险。它不会在发现阶段直接注入故障，而是说明需要什么混沌实验或压力测试才能确认风险。

接下来由用户决定是否执行。只有用户选择以后，Agent 才生成和运行实验，并解释结果，判断风险被确认还是被否定。

值得关注的变化是，Agent 不再只输出一句“我认为这里有风险”，而是把判断交给真实实验。但这页仍然只是行业趋势证据，不会被扩写成我们的 CI 方案。

同时要保留边界：Harness 公布的是产品机制，没有提供独立验证的风险预测准确率、MTTR 或事故率改善数据。

**来源与边界（不口播）**

- [Harness｜Find Resilience Risks Automatically, Then Confirm Them｜2026-08-24](https://www.harness.io/blog/find-resilience-risks-automatically-then-confirm-them)
- 边界：厂商产品发布；效果数据尚未独立验证。

### 讲者理解补充（不口播）

**韧性风险是什么：** 系统在部分服务变慢、节点故障、流量升高或依赖不可用时，是否还能保持可接受服务。它关注的不只是代码有没有 Bug，还关注系统面对真实压力和故障时会怎样。

**被动发现与主动验证的区别：** 被动发现只读取部署配置、Kubernetes 清单和历史数据，不向系统制造故障；主动验证会真正运行混沌实验或压力测试，因此影响更大，需要用户决定。

**混沌实验是什么：** 有控制地注入故障，例如终止一个 Pod、增加网络延迟或让某个依赖暂时不可用，观察系统是否能自动恢复。它不是随意破坏生产，而是有范围、有终止条件、有观察指标的实验。

**压力测试是什么：** 逐步增加请求量或并发，观察吞吐、延迟和错误率在哪个位置开始恶化。

**为什么这页放在趋势而不是实践：** Harness 的机制能说明“Agent 判断正在进入实验验证”，但它主要属于 CD 和韧性测试，并不是本次要深入讲解的纯 CI 方案。

## 第 9 页｜授权开始检查完整执行轨迹

第五个变化，是授权正在从单次权限检查转向完整轨迹检查。

传统权限可能只回答：这个 Agent 能不能调用某个工具？但“能够调用 Publish”并不代表此时此刻就应该 Publish。系统还需要知道前面发生了什么。

AWS Temporal Policies 展示了四类机制。

第一是顺序：前置步骤成功后才能执行后续动作。第二是一致性：当前参数必须匹配上一步系统真实返回的对象。第三是新鲜度：过期查询或扫描结果不能继续授权高风险动作。第四是人工审批和累计上限，用来限制高影响操作和失控循环。

这些规则位于 Agent 代码之外。即使 Agent 错误地声称“我已经检查过了”，外部策略系统仍然依据真实调用记录做 Allow 或 Deny。

需要明确的是，AWS 官方文章使用的是金融 Agent 示例。将这些机制理解为 CI/CD 的行业趋势，是本稿的场景映射，不是 AWS 原文提供的完整 CI/CD 实施方案。

**来源与映射边界（不口播）**

- [AWS｜Securing AI Agents with Temporal Policies](https://aws.amazon.com/blogs/machine-learning/securing-ai-agents-with-temporal-policies-in-amazon-bedrock-agentcore/)
- 边界：官方示例面向金融 Agent；CI/CD 表述为趋势映射。

### 讲者理解补充（不口播）

**Temporal Policy 可以怎么理解：** 普通权限只看“你有没有调用这个工具的资格”；时序策略还会查看之前发生过哪些动作、先后顺序是否正确、前面的证据是否仍然有效。

**映射到 CI/CD 的例子：** 发布制品前，系统可以要求同一个 Commit 已经完成构建；当前准备发布的 Artifact 必须正是刚刚测试和扫描的那个；扫描结果不能过期；高风险发布还需要人工批准。

**“对象一致性”为什么重要：** 如果测试的是制品 A，最后却把制品 B 传给发布工具，即使测试步骤显示成功，也不能证明 B 安全。策略需要检查步骤之间传递的是同一个对象。

**“新鲜度”为什么重要：** 三天前的扫描可能对应旧代码或旧依赖，不能无限期授权今天的新发布。证据需要明确有效期。

**为什么策略要放在 Agent 外部：** 如果规则只写在 Prompt 里，Agent 可能遗忘或错误理解。外部策略引擎可以基于真实事件强制拒绝动作。

**这一页的边界：** AWS 原文没有提供 CI/CD 实现，这些 CI/CD 例子只是帮助理解机制，演讲时必须明确是场景映射。

## 第 10 页｜Runner 成为核心信任边界

第六个变化，是 Runner 的安全地位正在上升。

Runner 连接三类东西。第一类是不可信输入，包括 Pull Request、Merge Queue 和外部文本。第二类是执行面，包括 Checkout、Cache、Build Script 和 Shell。第三类是高价值资产，包括 Secrets、GITHUB_TOKEN、制品写权限和内网访问。

一旦不可信输入穿过工作流进入脚本和缓存，它的影响可能不仅停留在当前 Job，还可能污染后续执行环境。

GitHub 最近的 CodeQL 2.26.3 改进了多类 GitHub Actions 查询，包括 merge_group 建模、不可信 Checkout、Cache Poisoning 和环境变量注入。GitHub 的安全文档也提醒，自托管 Runner 可能被不可信代码持续污染。

因此，分析不可信代码的 Job 应该默认只读、不携带 Secret，并与具有写权限的 Job 拆分权限、Workspace 和 Runner。Runner 不只是算力资源，而是 Agent 时代的核心信任边界。

**来源（不口播）**

- [GitHub｜CodeQL 2.26.3 improves GitHub Actions queries](https://github.blog/changelog/2026-08-19-codeql-2-26-3-improves-github-actions-queries-and-javascript-modeling/)
- [GitHub Docs｜Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use)

### 讲者理解补充（不口播）

**Runner 是什么：** Runner 是真正执行 CI Job 的机器或运行环境。构建脚本、测试、Shell 命令和第三方工具最终都在 Runner 上运行，所以它比流水线界面拥有更直接的系统能力。

**为什么 Pull Request 内容是不可信输入：** 外部贡献者可以控制代码、文件名、分支名甚至部分文本字段。如果工作流把这些内容直接拼进 Shell 命令，就可能产生命令注入或执行恶意代码。

**Cache Poisoning 是什么：** 一个不可信 Job 把被篡改的依赖或构建输出写入共享缓存，后续高权限 Job 从缓存读取并执行，风险就跨越了原来的 Job 边界。

**自托管 Runner 为什么更敏感：** GitHub 托管 Runner 通常按 Job 提供干净环境；长期复用的自托管 Runner 可能保留工作区、进程、缓存或配置，攻击影响可能持续到后续任务。

**拆分 Job 的实际含义：** 分析外部 PR 的 Job 只读取代码、不携带 Secret；需要签名、发布或写仓库的 Job 在另一个干净 Runner 上运行，并只接收经过验证的制品。

**现场可以用一句话解释：** “Runner 是代码真正获得执行权的地方，所以隔离和最小权限比模型是否聪明更基础。”

## 第 12 页｜实践一：GitLab 面向 Agent 重构 SCM

GitLab 认为，当 Agent 成为 Git 服务器的高频用户时，会出现三个结构性问题。

第一个是“完整克隆带来的传输税”（Clone Tax）。Agent 为了读取少量文件，先下载整个仓库；换一个 Agent 或者重新执行任务，又重复一次。

第二个是“并发崩溃”（Concurrency Collapse）。大量独立 Session 同时读取、写入和重试，会把面向人类规模设计的 Git 后端推到并发和可用性瓶颈。

第三个是“缺少隔离”（No Isolation）。多个 Agent 共享账号和分支空间，失败实验不容易干净丢弃，也很难回答究竟是哪个 Agent、哪个工作流、哪个模型做了什么。

GitLab 的做法不是取消 Git。Next-generation SCM 继续兼容 Git 协议，但重新设计后端和面向 Agent 的接口。Agent 仍然可以和原有 Git 工作流协同，但不必为了常见读取操作反复搬运整个仓库。

这套实践的定位很明确：它不是一个 Coding Agent，也不是一个 CI 修复器，而是支撑大量 Agent 并发读取、实验和提交的 SCM 执行基础设施。

**唯一主要来源与边界（不口播）**

- [GitLab｜Git was built for humans — agents need an upgrade](https://about.gitlab.com/blog/gitlab-next-gen-scm/)
- 本页没有引入其他公司的实现或跨来源参考架构。

### 讲者理解补充（不口播）

**什么叫“Agent 成为 Git 服务器的高频用户”：** 人通常一次 Clone 后在本地工作较长时间；Agent 可能被临时创建、并行执行、失败后重启，每个实例都重新读取仓库。使用者从几十个人变成数百或数千个短生命周期会话，访问模式就变了。

**完整克隆传输税：** 任务只需要少量文件，但系统移动了整个仓库及历史。浪费的不只是网络，还包括等待时间、磁盘、解压和 Agent 为搜索结果消耗的 Token。

**并发崩溃不一定指服务器真的宕机：** 更常见的是延迟明显增加、吞吐不稳定、队列堆积，导致 Agent 等待和重试进一步放大压力。

**隔离包含两层：** 数据隔离是每个 Agent 只看任务需要的内容；工作隔离是不同 Agent 的实验不会互相污染。归因则要求每个动作能关联到具体身份、工作流、模型和凭据。

**这不是 CI 自愈方案：** GitLab 这一实践主要解决 SCM 读取、写入和并发基础设施。它对 CI 有价值，是因为 Agent 的修改最终仍要进入构建、测试、策略和审计链路，但它本身不负责修复流水线。

## 第 13 页｜GitLab：服务器侧接口取代完整 Clone

具体看它的运行机制。

第一步，Agent 提出一个精确的取证请求，例如读取一组文件、获取两个版本之间的 Diff-stat，或者查询某条路径最后一次变更。

第二步，请求进入智能层，由它负责路由、缓存和后台工作。

第三步，后端使用可以按需扩展的计算层和对象存储层。GitLab 表示计算与存储通过标准 S3 API 交互，因此同样的架构既可以运行在 GitLab.com，也可以使用客户自己的对象存储或兼容 S3 的基础设施。

第四步，系统返回最小证据，而不是完整工作树。文章给出的典型接口包括 Batch Read、Diff-stat 和 Last Commit for Path。

GitLab 的早期内部测试报告，任务总耗时最高改善 50 倍，Token 最高减少约一半，网络流量最高减少 1000 倍。但 GitLab 自己明确称这些是测试最高值，不是生产保证。产品目前仍然处于私有测试阶段。

所以这一实践真正值得关注的是：代码仓库开始从“供 Agent 下载文件”，转向“直接向 Agent 提供结构化工程证据”。我们不需要假定自己也能得到同样倍率，才能看见这个基础设施方向。

**唯一主要来源与边界（不口播）**

- [GitLab｜Git was built for humans — agents need an upgrade](https://about.gitlab.com/blog/gitlab-next-gen-scm/)
- 边界：50×、2×、1000× 均为早期内部测试最高值；产品仍处于私有测试阶段。

### 讲者理解补充（不口播）

**智能层做什么：** 它类似仓库请求的调度中心，决定请求发到哪里、哪些结果可以从缓存返回、哪些后台维护任务需要执行。它不等于大模型，这里的“智能”主要是基础设施层的路由和协调。

**弹性计算和对象存储为什么分开：** 计算节点可以根据并发临时增加或减少；仓库数据放在独立对象存储中，不依赖某一台计算机器的本地磁盘。这样更容易横向扩展和恢复。

**S3 API 的意义：** 它是一种广泛使用的对象存储接口。兼容 S3 并不表示一定把代码放在 AWS，而是客户可以选择任何兼容该接口的云端或自建存储。

**三个接口怎样理解：** Batch Read 是一次读取多个指定文件；Diff-stat 返回变化规模和文件统计；Last Commit for Path 查询某条路径最近由哪次提交修改。它们把常见取证动作变成服务器能直接回答的问题。

**三个倍率分别指什么：** 50× 是任务总耗时最高改善；2× 表示 Token 用量最高约减半；1000× 是网络流量最高下降幅度。三者都来自 GitLab 自己的早期测试，并不一定在同一次任务里同时达到。

**私有测试阶段意味着什么：** 产品只向有限客户开放，接口、性能和可用性都可能变化。演讲中应该说“值得关注的架构方向”，不要说“已经成熟可大规模落地”。

## 第 14 页｜实践二：AWS 流水线失败自动调查

第二个实践直接发生在 CI/CD 失败以后。

AWS 8 月 17 日发布的技术文章，将 GitHub、AWS CodePipeline、Amazon CloudWatch、AWS Lambda 和 AWS DevOps Agent 连接成一条自动调查链路。

第一步，开发者向 GitHub 推送代码。第二步，CodePipeline 运行构建、测试和部署。第三步，CloudWatch 持续监控流水线指标和日志；当构建阶段失败、部署回滚或者下游健康指标越过阈值时，CloudWatch 进入告警状态。

第四步，告警触发 Webhook Executor Lambda。Lambda 解析事件负载，提取上下文，并向 AWS DevOps Agent 发送经过认证的结构化调查请求。

第五步，DevOps Agent 开始调查。它关联流水线阶段、CodeBuild 日志、GitHub Commit 和 Pull Request，识别失败与具体代码变更之间的关系。

最后，Agent 输出根因和修复建议，供工程师复查和执行。

这比一般的“把日志复制给聊天机器人”更接近一条工程流程：失败事件自动触发，输入带有明确上下文，调查跨越流水线、日志和代码历史，输出也保留审计记录。

**唯一主要来源（不口播）**

- [AWS｜用 CodePipeline 和 DevOps Agent 简化 GitHub 交付流程｜2026-08-17](https://aws.amazon.com/blogs/devops/streamline-your-github-journey-with-aws-codepipeline-and-aws-devops-agent/)
- 本页只描述该 AWS 官方参考架构。

### 讲者理解补充（不口播）

**每个组件的职责：** GitHub 保存代码和提交历史；CodePipeline 编排构建、测试与部署；CodeBuild 真正执行构建命令；CloudWatch 收集指标和日志并产生告警；Lambda 把告警转换成 Agent 能接收的结构化事件；DevOps Agent 负责跨这些数据调查。

**为什么需要 Lambda Webhook：** CloudWatch 告警本身主要描述监控事件，Agent 需要明确的应用、流水线、执行编号和错误上下文。Lambda 相当于适配器，解析原始告警、补充元数据，再发送经过认证的请求。

**“结构化事件”比复制日志好在哪里：** 它明确指出哪个流水线、哪个阶段、什么时间、哪个 Commit 失败。Agent 从一开始就有调查范围，不必在整套系统中盲目搜索。

**“关联”不是只做关键词搜索：** Agent 需要把时间线连接起来，例如某次提交之后 CodeBuild 开始失败，同时下游服务出现异常，从而判断代码变化与失败是否相关。

**自动调查不等于自动修复：** 这篇 8 月 17 日文章重点是自动发现、关联和给出修复建议。工程师仍需复查和执行。不要在演讲中把它说成“Agent 已经自动改代码并合并”。

## 第 15 页｜AWS：一次依赖拼写错误如何被定位

文章中有一个很适合说明机制的官方演示过程。

开发者把 `package.json` 中的依赖名称从 `express` 错写成 `expresss`，然后把变更提交到主分支。

CodePipeline 检测到代码推送并启动执行。到了 CI 阶段，CodeBuild 运行 `npm install`，因为这个错误的包名不存在，依赖安装失败。

失败事件触发调查以后，AWS DevOps Agent 读取 CodeBuild 日志，看到 `npm install` 的依赖解析错误。随后它把错误与最近一次 Commit 关联，确认问题由最新代码变更引入，而不是构建环境或下游服务导致。

最后，Agent 输出根因，并提供分步骤缓解计划，告诉工程师应该修正依赖名称以及如何验证。

这个例子说明，自动调查的价值不是让模型凭日志猜一个答案，而是把构建日志、失败阶段和最近代码变更关联在同一个调查上下文里。

同样要保留边界：这是 AWS 官方参考架构和示例应用，不是第三方客户生产数据。文章没有提供独立验证的根因准确率、错误归因率、建议采纳率或者 MTTR 改善比例。因此我们可以讲清它怎样运行，但不能把它包装成已经普遍验证的效果承诺。

**唯一主要来源与边界（不口播）**

- [AWS｜用 CodePipeline 和 DevOps Agent 简化 GitHub 交付流程](https://aws.amazon.com/blogs/devops/streamline-your-github-journey-with-aws-codepipeline-and-aws-devops-agent/)
- 边界：AWS 官方 Sample；无独立准确率或 MTTR 数据。

### 讲者理解补充（不口播）

**为什么这个错误适合演示：** `expresss` 是一个不存在的包名，`npm install` 会稳定失败，日志中也有明确错误。它能清楚展示 Agent 如何从失败日志追溯到最近提交，而不会被复杂业务逻辑干扰。

**症状和根因的区别：** 症状是“CodeBuild 的 npm install 失败”；根因是“最新提交把 express 拼错成 expresss”。如果只重复症状，就没有完成调查。

**为什么还要关联 Commit：** 同一种安装错误可能来自网络、软件源、锁文件或者包名。把日志与最近代码变化关联，才能判断最可能由哪次修改引入，并找到责任范围。

**缓解计划是什么：** 它不是一段泛泛建议，而应该包含修正哪个文件、恢复什么值、重新运行哪些检查、怎样确认问题消失。计划仍要由工程师复查，因为 Agent 可能归因错误。

**MTTR 是什么：** Mean Time to Recovery/Repair，平均恢复或修复时间。文章描述机制和样例，但没有提供独立统计证明它让真实客户的 MTTR 降低了多少。

**为什么不能只看这一个成功样例：** 一个稳定、明显的拼写错误比复杂并发、权限或偶发失败容易诊断。要评估产品可靠性，还需要大量不同类型失败、错误归因率和人工接受率等数据。

## 第 16 页｜如果只能带走 5 条

最后，如果今天只能带走五条，我希望是下面五条。

第一，CI 性能就是 Agent 产能。高频循环会放大慢检查、Flaky Check 和环境不一致。

第二，仓库正在变成证据查询服务。面向 Agent 的服务器侧接口开始替代完整 Clone 和本地重复搜索。

第三，流水线全绿只是准入，不是完成证明。对于迁移和移除任务，还要验证目标是否真实发生。

第四，Runner 是核心信任边界。不可信输入、可执行脚本和企业凭据不能被放在没有隔离的同一个环境里。

第五，流水线失败可以自动进入调查。系统可以自动把失败阶段、构建日志和最近 Commit 关联起来，再向工程师提供根因和修复建议。

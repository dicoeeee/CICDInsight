# 研究 Charter

## 1. 决策问题

面向 CTO、研发效能负责人和平台工程负责人，回答三个决策：

1. 代码仓、流水线、构建系统和制品仓需要新增或强化哪些基础设施能力，才能承接编码 Agent 带来的变更量与执行方式？
2. 哪些能力可以进入 12—24 个月平台路线图，哪些只适合试验或观察？
3. 如何避免把 Agent 的工具可调用性误当成授权、验证或发布权？

## 2. 研究对象

| 对象 | 本专题关注点 |
|---|---|
| 代码仓与代码托管平台 | Agent 任务入口、Issue/PR 协作、仓库上下文、MCP/API/CLI、Ruleset、身份、审批与审计 |
| CI 流水线 | Agent Step、动态调查与修复、反馈闭环、并发、日志结构化、预算和失败路由 |
| 构建系统 | 构建图、增量计算、远程缓存/执行、可复现环境、Agent 沙箱、自愈与验证 |
| 制品仓与包管理 | 依赖情报、制品查询与操作、SBOM、Provenance、Attestation、签名、晋级和策略 |
| 横切控制 | 工作负载身份、委托授权、Secret/网络隔离、独立 Oracle、审计、成本与效果度量 |

## 3. 时间窗

- **基线：** 大模型广泛进入软件开发前的传统 CI/CD 形态，用于辨别哪些能力早已存在。
- **重点观察窗：** 2023-01-01 至 2026-07-28。
- **重点增量窗：** 2025-01-01 至 2026-07-28，用于产品状态与 Agent 原生接口核验。
- **访问日：** 2026-07-28。

## 4. 核心分析框架

不按厂商罗列功能，而按六个问题检验变化：

1. **接口变化：** 人类 UI 是否扩展为机器可发现、结构化、可审计的 Tool/CLI/API/Skill？
2. **负载变化：** 人类节奏的提交是否变成高频、并行、长时 Agent 会话及多轮验证？
3. **控制拓扑变化：** 单次流水线是否分化为 Agent 概率性内环与确定性外部门禁？
4. **信任变化：** 静态服务账号是否演进为按任务委托、短期、最小权限的工作负载身份？
5. **证据变化：** Pass/Fail 是否扩展为 Commit、构建环境、制品摘要、Provenance、Agent Session 和批准链的可追溯图？
6. **经济性变化：** Runner 分钟是否扩展为并发、缓存命中、反馈延迟、推理成本、尝试次数和 Verified Outcome 成本？

## 5. 证据标准

- 优先级：官方文档/规范/源代码/发布说明/第一方工程实践/原始论文。
- 产品存在性、产品状态、机制、生产效果和行业普遍性分别判断。
- 厂商能力存在可由一手材料证明；效果数据若只有厂商自述，必须标注，不外推。
- 关键数字、版本、状态和日期逐项核对；无日期文档标记 `published: n/a`。
- 关键结论尽量由两类独立证据支撑：至少一个产品/规范机制，加一个跨厂商案例或原始研究。
- “尚未找到变化证据”不等于“没有变化”；保留证据缺口。

## 6. 非目标

- 不复述从提交到部署的传统 CI/CD 基础知识。
- 不研究模型训练、推理服务、RAG 平台或 AI 应用自身的 MLOps/LLMOps。
- 不比较基础模型编码能力。
- 不把 MCP、CLI 或 API 可调用等同于 Agent 已被授予生产写权。
- 不把一次 CI 变绿等同于业务正确、制品可信或可发布。
- 不为没有 Deep Dive 证据的 Presentation 页面直接补写事实。

## 7. 完成与阻塞条件

### 完成条件

- 四类基础设施均有至少两个独立案例或一个案例加一个规范/原始研究；
- 每项核心主张都记录事实、分析推断、限制和置信度；
- 明确区分“新增能力”“既有能力升级为关键基础”“尚未发生的营销主张”；
- 报告包含反例、成熟度判断和企业演进顺序；
- 完成逐主张事实审计后再决定 `presentation_ready`。

### 阻塞条件

- 关键产品状态无法核验；
- 关键写操作的授权、审计或执行边界不清；
- 仅有厂商营销页而无文档、发布记录或可检查实现；
- 关键结论依赖单一厂商效果数据且无边界说明。

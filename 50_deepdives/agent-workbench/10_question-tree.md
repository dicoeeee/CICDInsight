# Agent 工作台、专家团与交付角色重构问题树

## Q0：什么变化足以称为“Agent 工作台”？

- Q0.1 用户是否以目标、约束和验收标准发起任务，而不是逐条操作工具？
- Q0.2 工作面是否保留项目文件、指令、连接来源和历史任务上下文？
- Q0.3 用户是否能看到计划、子任务、过程状态、问题和产物？
- Q0.4 用户是否能暂停、改方向、补充上下文和批准重要候选动作？
- Q0.5 这只是聊天体验，还是可以沉淀为组织复用的工作入口？

## Q1：专家团是否是可核验的产品机制？

- Q1.1 是否存在显式的主 Agent/团长？
- Q1.2 是否能将任务拆成相互独立的子任务并行执行？
- Q1.3 专业 Agent 的角色、指令、模型、工具和上下文能否差异化？
- Q1.4 交接与整合由谁负责，冲突如何暴露？
- Q1.5 多 Agent 的额外 Token、时延、失败和写冲突是否被计量？

## Q2：谁设计和供应 Agent 能力？

- Q2.1 Skill、专家、工具、连接器和上下文由谁注册与版本化？
- Q2.2 谁能创建、测试、分享、发布、撤回和停用 Agent？
- Q2.3 权限是否来自宿主系统、短期身份和工具 Allowlist，而非 Agent 自我声明？
- Q2.4 是否有任务集、回归评测、成本预算、审计和生命周期 Owner？
- Q2.5 发布、运维、SRE、平台、安全与业务开发如何分工？

## Q3：Agent 工作台如何进入 CI/CD？

- Q3.1 哪些交付任务适合作为开发者自助入口：构建准备、失败诊断、发布就绪、恢复建议？
- Q3.2 哪些动作只能生成候选：代码修复、配置变更、部署计划、回滚建议？
- Q3.3 哪些系统继续做最终接受：Test、Scan、Policy、Signature、Approval、SLO、Rollback？
- Q3.4 Agent 身份、触发人身份、Pipeline 身份和审批者身份如何分离？
- Q3.5 如何避免工作台直接成为高权限生产跳板？

## Q4：职责迁移能否写成行业事实？

- Q4.1 产品机制是否支持“开发者消费、平台团队供给”的结构？
- Q4.2 是否存在跨企业数据证明发布/运维人员已把主要时间迁移到通用 Agent Harness 设计？
- Q4.3 哪些变化是趋势判断，哪些只是目标 operating model？
- Q4.4 有哪些反例：小团队、低频交付、高耦合任务、强监管环境、低质量平台？
- Q4.5 如何表达角色重构而不暗示岗位消失或责任分离消失？

## 假设与证伪条件

| 假设 | 支持条件 | 证伪或降级条件 |
|---|---|---|
| H1：Agent 工作台正在成为复杂交付任务的新入口 | 至少两个独立产品证明目标、上下文、过程与产物工作面 | 只能证明单次聊天或演示，缺少任务状态与产物机制 |
| H2：专家团是通用 Agent Harness 的可配置协作模式 | 有主 Agent/团长、专业 Agent、并行、交接与汇总证据 | 只有多个独立机器人，无共同任务图和整合机制 |
| H3：使用层与供给层正在分离 | 同时存在最终用户入口和 Builder/Admin 控制 | 同一用户只能手工配置全部工具和权限，无法组织复用 |
| H4：交付角色会向通用 Agent Harness 设计上移 | 产品机制 + 平台工程研究支持目标 operating model | 没有跨企业岗位数据时不得升级为已发生行业事实 |
| H5：Agent 不能替代 CI/CD 接受边界 | CI/CD 原生案例保留 Safe Output、Policy、Required Check 或审批 | 若产品允许 Agent 无外部校验直接取得生产授权，则主张需重写 |

## 结论门禁

- H1—H3 有一手产品机制即可形成高或中高置信分析；
- H4 只进入“企业建议/中置信推断”，直至有跨企业职责数据；
- H5 必须以 CI/CD 原生一手案例核验，并作为 Presentation 页脚硬边界。
